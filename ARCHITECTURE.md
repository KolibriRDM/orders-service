# Архитектура orders-service

`HTTP → handler.Handler → service.Service → repository.Repository → PostgreSQL`

`cmd/orders/main.go` собирает зависимости. Handler объявляет интерфейс Service,
service — интерфейс Repository. Конструкторы: NewHandler, NewService,
NewRepository. Внутренние слои не импортируют конкретные адаптеры.

- `handler` читает HTTP/JSON, задаёт deadline и переводит ошибки в HTTP.
- `handler/dto` содержит транспортные модели и преобразования.
- `service` выполняет бизнес-сценарии через небольшие интерфейсы зависимостей.
- `model` хранит бизнес-типы и правила без HTTP, protobuf и pgx.
- `repository` выполняет SQL; `repository/entity` нужен только при отличии формы данных БД.
- `errors` содержит ошибки, проверяемые через errors.Is.
- `platform` содержит только локальные технические компоненты.

Другие сервисы не подключаются Go-импортами. Сетевые DTO принадлежат адаптерам,
бизнес-модели не публикуются в общем пакете. Собственные миграции и роль БД
исключают необходимость читать чужие таблицы.

Архитектурный тест проверяет направление импортов и отсутствие зависимостей
на проекты других сервисов. Собственный go.mod, Dockerfile и тесты позволяют
собирать проект вне общей папки food-delivery.

После разделения поведение HTTP и SQL сохранено. gRPC и Kafka подключаем
отдельными этапами с проверкой контрактов и отказов.
