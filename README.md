# orders-service

Самостоятельный Go-проект и Git-репозиторий сервиса заказов Food Delivery.
Go 1.27.1; модуль `github.com/KolibriRDM/orders-service`.
Путь модуля подготовлен для будущего репозитория; remote пока не настроен.

## Разработка

```sh
cp .env.example .env # только если .env ещё отсутствует
make build
make test
make race
make vet
make run
```

При разделении существующий локальный `.env` уже перенесён. `make run` загружает
его; сам бинарник читает переменные окружения. Настоящие пароли в Git не входят.
Сборка и unit-тесты не требуют соседних проектов, `go.work` или `replace`.

## PostgreSQL и совместный запуск

Этот сервис владеет `orders_db` и ролью `orders_app`. Локальный PostgreSQL слушает
`127.0.0.1:15432`; SQL-миграции принадлежат этому репозиторию: `migrations/`.
Небольшой `internal/platform` также локальный: общего Go-проекта платформы нет.

В соседнем `../infrastructure`:

```sh
make db-up
make migrate
make seed-catalog
```

После этого запусти `make run` в отдельном терминале каждого сервиса.
HTTP этого сервиса: `http://127.0.0.1:8080`; `/healthz` проверяет процесс,
`/readyz` — его собственную БД. Сервисы останавливаются и перезапускаются отдельно.

Интеграционные тесты с временной БД запускаются из `../infrastructure`:

```sh
make test-orders-postgres
```

Без инфраструктурного репозитория можно подготовить отдельную тестовую БД,
применить `migrations/` и передать `ORDERS_TEST_DATABASE_URL` и
`ORDERS_TEST_DB_PASSWORD`, затем выполнить `make test-integration`.
Имя тестовой БД должно начинаться с `orders_test_`; рабочая БД не подходит.

## Контейнер

```sh
docker build -t food-delivery/orders:local .
```

Образ собирается из одного этого репозитория. Процесс работает без root.
Конфигурация передаётся окружением; `.env` исключён из build context.
При запуске в контейнере адрес БД должен указывать на доступный контейнеру
PostgreSQL, а не на `127.0.0.1`. Аналогично `CATALOG_GRPC_ADDR` должен указывать
на адрес контейнера каталога, например `catalog-service:9082` в общей Docker-сети
с таким именем или сетевым alias. Совместный Compose приложений пока не реализован.

## API заказов

- `POST /v1/orders` — создание с `X-Demo-User-ID` и `Idempotency-Key`.
- `GET /v1/orders/{id}` — чтение своего заказа с `X-Demo-User-ID`.

Новый заказ возвращает 201 и Location, совпадающий повтор — 200;
изменённый запрос с тем же ключом — 409. Чужой заказ скрывается за 404.
Позиции, заказ, ключ и outbox-событие сохраняются одной SQL-транзакцией.
Старые заказы хранят снимки названий и цен. Сохранённый повтор обрабатывается
до обращения к каталогу; недоступность catalog не мешает чтению старого заказа.

## Связь с каталогом

`internal/catalogclient.Client` реализует интерфейс `service.CatalogProvider`
через gRPC `/food.catalog.v1.CatalogService/ResolveItems`. Внутренние Go-пакеты
каталога не импортируются; protobuf-ответ преобразуется в локальную `model.MenuItem`.

Соединение создаётся один раз при запуске, переиспользуется конкурентными
запросами и закрывается при остановке orders. Конструктор не проверяет доступность
каталога: сетевое подключение начинается при RPC. Локальный стенд работает без TLS.

Каждый вызов получает дочерний контекст с таймаутом 500 мс. Более ранний deadline
и отмена исходного запроса сохраняются. Размер входящего и исходящего
protobuf-сообщения ограничен 64 КиБ. Настроенные политики повторных вызовов отключены;
прозрачные транспортные повторы библиотеки gRPC этим не исключаются.

`InvalidArgument` преобразуется в `ErrInvalidInput`, `NotFound` — в `ErrNotFound`,
остальные ошибки RPC — в `ErrCatalogUnavailable`. Отмена исходного запроса имеет
приоритет; истечение только таймаута каталога означает его недоступность.
Клиент проверяет ресторан, состав блюд, дубликаты, названия и цены и восстанавливает
порядок ID запроса. Частичный результат не возвращается.

`/readyz` проверяет собственную БД orders и не зависит от доступности каталога.
При отказе каталога новый заказ получает 503, а чтение заказа и сохранённый
идемпотентный повтор продолжают работать.

## Настройки

| Переменная | Значение по умолчанию / назначение |
| --- | --- |
| `ORDERS_HTTP_ADDR` | `:8080`, адрес HTTP-сервера |
| `CATALOG_GRPC_ADDR` | `127.0.0.1:9082`, адрес каталога в формате `host:port` |
| `ORDERS_DATABASE_URL` | Обязательная строка подключения к своей БД |
| `ORDERS_DB_PASSWORD` | Обязательный пароль своей роли БД |
| `LOG_LEVEL` | `info` |

В адресе каталога не нужны `http://` и путь метода. Прежняя переменная
`CATALOG_BASE_URL` больше не используется.

## Контракт и генерация

Каталог владеет protobuf-контрактом. Orders хранит его точную копию в
`api/proto/catalog/v1/catalog.proto` и самостоятельно генерирует Go-код.
Для обновления из соседнего каталога, из корня orders-service:

```sh
cp ../catalog-service/api/proto/catalog/v1/catalog.proto api/proto/catalog/v1/catalog.proto
make generate
```

Нужны Buf `1.72.0`, `protoc-gen-go v1.36.12` и `protoc-gen-go-grpc 1.6.2`.
`buf.gen.yaml` назначает сгенерированному коду путь модуля orders-service.
Файлы `catalog.pb.go` и `catalog_grpc.pb.go` являются частью исходников и должны
попадать в Git вместе с контрактом; их не редактируют вручную. Обычная сборка,
включая Docker, использует готовые файлы и не требует генераторов или исходников
catalog-service. Соседний проект нужен только при обновлении копии контракта.

## Проверки и оставшаяся работа

Тесты клиента проверяют параметры RPC, deadline, отмену, ошибки, закрытие
соединения и некорректные ответы. Сетевые тесты проверяют лимиты сообщений,
отмену на стороне сервера и конкурентное использование одного клиента.
Из `../infrastructure` команда `make test-day2` проверяет полный сценарий
с двумя отдельными процессами и PostgreSQL.

`repository/memory` сохранён вместе с тестами, но приложение его не использует.
SQL-репозиторий outbox читает готовые события, отмечает публикацию и назначает
повторную попытку. `internal/kafkapublisher` отправляет сохранённый payload через
franz-go с ключом `order_id` и ожидает подтверждение Kafka до 5 секунд.
При ошибке сохраняются `ErrPublishFailed` и исходная причина; отмена родительского
контекста возвращается отдельно. Таймаут не исключает последующую доставку.
`OutboxService.PublishBatch` последовательно обрабатывает до 20 событий:
подтверждённую отправку отмечает в БД, при ошибке назначает повтор с растущей
задержкой и случайным разбросом до 30 секунд. Каждая операция БД ограничена
двумя секундами. Ошибка БД останавливает пачку, сохранённый retry позволяет
продолжить обработку следующих событий.
Relay подключён в main: первый проход запускается сразу, последующие — через
секунду после завершения пачки. Настройки: `KAFKA_BROKERS` (через запятую,
по умолчанию `127.0.0.1:19092`) и `ORDER_CREATED_TOPIC` (по умолчанию
`food.order-created.v1`). При запуске в Compose адрес брокера — `kafka:9092`.
Ошибки Kafka не останавливают HTTP; ошибки БД логируются, цикл пробует снова.
При завершении процесс отменяет relay и ждёт его до закрытия Kafka-клиента и БД.
Consumer notifications сохраняет уведомление по событию, а повторную доставку распознаёт по event_id.

Из infrastructure команда `make test-orders-relay` проверяет настоящий процесс
orders, доставку outbox, накопление при отказе отдельного тестового Kafka-брокера,
восстановление без перезапуска orders и остановку по SIGINT/SIGTERM.

Тест publisher на локальной Kafka создаёт временный топик с тремя партициями,
проверяет доставку и одинаковую партицию для одного заказа, затем удаляет топик:

```bash
KAFKA_TEST_BROKERS=127.0.0.1:19092 go test -tags=integration -race -count=1 -run '^TestPublisherKafka$' -timeout 60s -v ./internal/kafkapublisher
```

Kafka должна быть запущена командой `make kafka-up` из infrastructure.


## Метрики и JSON-логи

`GET /metrics` экспортирует отдельный реестр процесса (`http://localhost:8080/metrics`).
Для работающего Compose потребуется пересборка приложения.

- `food_http_requests_total{service="orders-service",method,route,status}` — число HTTP-запросов.
- `food_http_request_duration_seconds{service="orders-service",method,route}` — длительность запросов в секундах.
- `food_outbox_pending_events{service="orders-service"}` — все неопубликованные события, включая отложенные повторы.
- `food_outbox_oldest_pending_age_seconds{service="orders-service"}` — возраст самого старого неопубликованного события.
- `food_outbox_stats_up{service="orders-service"}` — успешность последнего измерения: 1 или 0.

Статистика читается сразу после запуска и через 5 секунд после каждого завершённого
опроса. SQL ограничен двумя секундами; отдельная горутина продолжает измерения при
задержках публикации в Kafka. При ошибке сохраняются предыдущие pending/age, а
stats_up становится 0; до первого успешного измерения все три показателя равны 0.
Пустая очередь даёт pending=0 и age=0. Возраст вычисляется по времени PostgreSQL
и ограничен снизу нулём. Перед закрытием зависимостей main ждёт обе фоновые горутины.

HTTP использует шаблоны маршрутов без UUID, неизвестные пути — `unmatched`, методы —
`OTHER`. `/metrics`, `/healthz` и `/readyz` исключены из прикладного RPS.
Если ответ ещё не отправлен, отмена отмечается диагностическим 499, дедлайн — 504;
эти коды middleware не отправляет клиенту. ID присутствуют только в логах, не в labels.

JSON-лог `order creation handled` связывает request_id и order_id; created=false
означает идемпотентный повтор. `outbox event published` связывает order_id и event_id
после подтверждения Kafka и успешной отметки БД. Повторы публикации также содержат
эти ID; ошибка обновления БД сохраняет их в контексте ошибки пачки. Payload, адрес
доставки и ключ идемпотентности в эти записи не включаются.
